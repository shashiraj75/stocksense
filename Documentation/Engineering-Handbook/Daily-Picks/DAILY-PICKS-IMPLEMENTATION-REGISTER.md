## Governance rule

No Daily Picks item may be called complete from a chat summary, test result, commit, merge, or deployment alone. The terminal implementation state is **PRODUCTION VERIFIED**. Statistical or effectiveness work may remain **MONITORING** after production verification until sufficient real outcomes accumulate.

Every future Daily Picks implementation must:

1. cite one or more permanent `DP-###` IDs;
2. update this register in the same implementation commit where practical;
3. record exact files, tests, commit SHA, deployment evidence, production evidence, and remaining work;
4. preserve a truthful distinction between production-active, shadow-only, validation-only, and documentation-only work;
5. never enable `LEARNING_ALPHA_PRODUCTION_ENABLED` as an incidental part of another item.

| SUPERSEDED | Replaced by another controlled item. |

**Compound status note (added 2026-07-21, DP-026):** none of the values above distinguishes "the underlying defect was corrected" from "the underlying defect was disclosed but left in place" — `IMPLEMENTED — LOCAL` on its own describes a merge state, not a remediation state, and using it alone for a disclosure-only change risks a reader assuming the defect itself was fixed. Where a finding is disclosed rather than remediated, the register uses the explicit compound label `VERIFIED — disclosure containment implemented locally, defect NOT remediated`, built from this table's own `VERIFIED` and `IMPLEMENTED — LOCAL` values rather than inventing an unrelated new category. This is not itself a new controlled status for general reuse — it is reserved for cases identical in kind to `DP-026` (a finding where the finding-table description remains fully true and unchanged, and only a disclosure was added).

### DP-033 readiness-audit evidence (2026-07-22, Final Architecture and Backfill Readiness Remediation)

This session's own prior report (draft PR #12's original description) is corrected below rather than trusted at face value, per explicit instruction. Every item is either fixed in code/tests this session or explicitly recorded as still open.

**1. Architecture correction.** The prior claim ("Option B-equivalent (immutable-per-request-cache)") was wrong — a 12h in-memory cache (`sec_edgar_adapter.py`'s `_facts_cache`) is NOT immutable persistence: it does not survive process restart, is not shared across Railway instances, and a live re-fetch after expiry can return a materially different payload with no record of what was actually used the first time. **True architecture implemented this session:** `services/sec_pit_store.py` — an actual immutable, migration-backed Postgres/SQLite table (`sec_pit_facts`, unique on `(cik, concept, unit, accession, period_end)`). `validation_engine.py`'s `_get_fundamentals_as_of_persisted_first()` reads from this table FIRST; a live SEC fetch happens at most once per CIK per process (tracked via `_pit_ingested_ciks`), and every subsequent as-of lookup — including a second backtest run in a fresh process — reads only the persisted rows. Confirmed via test (`test_dp033_persisted_ingest_wiring.py`) that a stubbed-to-explode live fetch function is never called on the second/third/... lookup for an already-ingested CIK.
- Calls SEC EDGAR during every uncached execution? **No** — exactly once per CIK per process, proven by test.
- Depends on live network during replay? **No**, once ingested — the offline lookup (`get_facts_as_of_persisted()`) makes zero network calls, proven by test.
- Retains the exact SEC payload used for a completed run? **Yes** — every fact row persists with its own accession/form/filed date.
- Reproduces the same result after SEC data changes? **Yes** — a later live change to SEC's answer for the same accession cannot alter an already-persisted row (rows are `INSERT ... ON CONFLICT DO NOTHING`, never updated); an amendment ships as a NEW row (new accession), never a mutation.
- Retains filing/accession/version provenance? **Yes** — `accession`, `form`, `fiscal_year`, `fiscal_period` columns.
- Survives process restart? **Yes** — real Postgres/SQLite table, not in-memory.
- Prevents later amendments from changing a repeated historical result? **Yes** — proven by test (`test_amendment_filed_after_cutoff_does_not_leak_backward`).
- Multi-instance/concurrent-safe? **Partially proven** — Postgres `ON CONFLICT DO NOTHING` is atomic and safe under concurrent ingestion of the same accession from multiple instances; SQLite path is single-process/test-only (matches every other dual-path table in this repo, e.g. `val_runs`/`val_signals`). Not load-tested under real concurrent production traffic this session.

**2. #### DP-025 quality-provenance correction (2026-07-18, same day, one confirmed production-contract mismatch)

The hardening commit `55e4c4750c66824e33d27157dde5ff4b25880736` above originally misread the quality fallback contract: it assumed `quality_available=False → quality_score=None`. That does not match production. `_predict_stock()`'s real contract is:

```python
"quality_score": qf.get("score") if qf.get("score") is not None else 50,
"quality_available": _quality_available,
"quality_raw_score": _quality_raw,
```

i.e. unavailable quality evidence legitimately produces `quality_available=False, quality_raw_score=None, quality_score=50` (the neutral ranking fallback) — `quality_score=None` was never a real production state. `CandidateSnapshot` previously had no `quality_raw_score` field at all, so it could not distinguish a genuine score of 50 from a fabricated fallback of 50.

- Corrected quality contract: `CandidateSnapshot` gained an additive `quality_raw_score: float | None` field (the genuine pre-fallback value; `None` means unavailable; a genuine `0` is preserved exactly, never truthiness-coalesced) and `quality_raw_score_provided: bool` (distinguishes an explicitly-declared `None` from a pre-2026-07-18 fixture that never mentions the field at all — see backward compatibility below). `contracts.validate_structure()`'s quality rule was replaced with the exact production contract: when `quality_available=True`, requires `quality_raw_score` finite and `quality_score == quality_raw_score` (within float tolerance); when `quality_available=False`, requires `quality_raw_score is None` and `quality_score == 50` exactly; NaN/Infinity rejected in either field; a genuine `quality_score=0`/`quality_raw_score=0` is explicitly accepted as real evidence, never coalesced.
- Backward-compatible fixture handling: `quality_raw_score_provided` is derived from the JSON key's PRESENCE (`"quality_raw_score" in d`), not its value — a fixture that explicitly writes `"quality_raw_score": null` correctly declares "confirmed unavailable" (`provided=True`, treated as normal), while a fixture that omits the key entirely is marked `provided=False` ("unknown provenance", never inferred as either genuine or fallback). `contracts.validate_structure()` skips the quality consistency checks entirely for a `provided=False` candidate (nothing to check); `pipeline_replay._assess_strict_integrity()` (STRICT-only) now refuses replay when any candidate has `provided=False`, exactly like the other point-in-time-only categories. Failure classification: K — more than one contributing factor, with D (controlled memory abort) as the dominant, addressable root cause.** Ruled out A/B (scheduler fired, backend received it — confirmed via the GitHub Actions run log and the durable `daily_picks_jobs.started_at` row) and C (a durable job row WAS reserved — the failure is mid-run, not pre-reservation). **3. Root cause — genuinely new finding, going back to 2026-07-15.** `daily_picks_jobs` history shows the identical failure signature (OOM-kill, orphaned/stuck job, or — since yesterday's circuit breaker — a controlled abort) recurring on 07-15, 07-16, 07-17 (x2), 07-20/21, and 07-22, always mid-Phase-1 or entering `ranking`, always with `processed` in the 350-1000 range out of ~1,185-1,191. The 2026-07-21 fix (bounding the Phase 1 loop to a plain sequential loop, one task's Future/result alive at a time) removed one real leak but did not change the failure signature, because it left Phase 1 building and holding **all three horizons'** full candidate pools (`raw`, ~1,191 rich result dicts — reasoning text, quality-factor breakdowns, global-context dicts) simultaneously, releasing them only one at a time in the ranking loop AFTER Phase 1 fully completed. The true peak — all 3 horizons resident, about to release one at a time — was unchanged by that fix. Today's abort at 570/1,191 (mid-Phase-1, before the release loop could run even once) is direct, executable confirmation.

**4. Permanent fix — horizon-bounded Phase 1.** `_generate_picks_inner` (`backend/services/daily_picks.py`) restructured so each horizon's candidates are scored (Phase 1), ranked/selected (Phases 3-6), persisted, and released — via `del`/going out of scope, immediately at the top of the next loop iteration — **before the next horizon's Phase 1 scoring even begins**. The flat `tasks`/`raw` variables (spanning all 3 horizons) no longer exist; each horizon builds its own `items` list. This is a strictly stronger guarantee than "release promptly after capture" (the 07-21 fix's approach): there is nothing spanning multiple horizons to release in the first place. Peak retained Phase-1 memory drops from ~3 horizons' worth (~1,191 rich dicts) to 1 (~397) — empirically confirmed via a large synthetic-workload test (`tests/regression/test_daily_picks_memory_bound_synthetic_workload.py`) that gc-tracks live object counts through a full synthetic run. Output equivalence proven two ways (`tests/regression/test_daily_picks_horizon_bounded_memory.py`): (a) the exact call sequence to `_predict_stock` covers every (symbol, horizon) pair exactly once, reordered to horizon-major but otherwise identical; (b) the downstream ranking/selection pipeline, fed the same candidate set in two different orders, produces byte-identical selected symbols/ranks/scores. `_N_CANDIDATES`/`_TARGET_UNIVERSE_SIZE` (400) and `DAILY_PICKS_MEM_ABORT_PCT` (80%) are both unchanged — explicitly guarded by regression test (`test_daily_picks_incident_isolation_and_mutation_guards.py`).

**5. Empty-payload-overwrite correction (the actual cause of the indefinite blank page).** Independent of the memory root cause: `generate_picks()`'s exception handler used to write an empty, error-tagged payload to BOTH the disk cache file and Postgres's `daily_picks_cache` table — and `load_picks_from_db()`/`get_cached_picks()` served whichever row was most recently written, success or failure. This silently shadowed the last genuinely successful payload every single time ANY failure occurred (not just today's), which is the direct, immediate cause of the page going blank rather than showing yesterday's (or last week's) picks with a staleness notice. Fixed: the failure path no longer writes to either store at all (the failure is durably recorded exclusively via `mark_daily_picks_job_failed`/`daily_picks_jobs`). `daily_picks_cache` gained a `status` column (`'success'` | `'failed_attempt'`, default `'success'`); `save_picks_to_db` always writes `'success'` (the only status any live code path writes now); `load_picks_from_db` filters `WHERE status = 'success'`. A one-time, idempotent migration backfill (`UPDATE ... WHERE status='success' AND payload ? 'error'`) retroactively corrects any row already polluted by this bug before the fix — self-healing, no manual cleanup script needed. `picks_generated_today()` no longer additionally requires non-empty picks (that was itself a workaround for the same bug) — a genuine, legitimate zero-BUY successful day is now correctly distinguished from failure.

**6. API/UI contract.** `GET /api/picks/daily` and `GET /api/picks/status` gained `stale`, `serving_stale_payload`, `last_successful_session_date`, `last_attempt_status`, `last_attempt_error_category` (a small closed set of safe categories — `memory_limit_exceeded`, `persistence_failed`, `provider_timeout`, `provider_connection_error`, `provider_rate_limited`, `unknown` — never a raw traceback; the previous `last_error` field's raw-traceback exposure is also closed by this change). Frontend (`frontend/src/app/picks/page.tsx`) shows "Today's {market} generation is delayed. Showing the last successfully completed {market} picks from {date}." when serving a stale payload, and distinguishes "Generation completed — no stocks met today's qualification criteria" (a legitimate empty day, `generated_at` is today) from "No BUY signals in the last completed run" (stale — the empty result is from an earlier date, today's run may still be pending).

**7. Watchdog / bounded governed recovery.** `attempt_governed_recovery(market, reason)` (`daily_picks.py`) is called from the US premarket finalizer (`premarket_finalizer.py`) whenever its own Stage-1 validation finds today's base payload genuinely missing or stale (`skipped_no_base`/`skipped_stale_base` — deliberately excluding `rejected_malformed_base`, a data-integrity problem a blind retry could mask rather than fix). This is a real, working recovery path riding on the finalizer's existing GitHub Actions cron (fires ~4-5.5h after the base's expected completion — not the ideal sub-20-minute SLA a dedicated scheduler would give, honestly documented as a residual gap, not a false claim of tight bounds) rather than a brand-new scheduling mechanism. `_last_trigger_received_at` remains in-memory-only (does not survive a Railway restart) — a documented, not-fully-closed observability gap; `daily_picks_jobs.started_at` is the durable substitute already relied on for the watchdog's own bounding logic.

## DP-034 — Conviction-gated Daily Picks publication policy (implementation status, not yet deployed)

**2. Conclusion: PROVEN SUITABLE for reuse as the publication gate. It is relabeled "Model Conviction" for publication-policy purposes only (see `services/thresholds.py`'s `DailyPicksPublicationThresholds` docstring) — the underlying field, computation, and existing "Signal Strength" display are unchanged.
